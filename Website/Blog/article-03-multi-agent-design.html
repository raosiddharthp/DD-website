Designing multi-agent systems that don't become multi-agent messes

"Agent swarm" is an architectural smell if you haven't first defined what each agent owns, where its authority ends, and what the system does when it fails.

Siddharth Rao  ·  May 2026  ·  17 min read

There is a moment in every multi-agent system design that reveals whether the architect is thinking in agents or thinking in architecture. It usually happens during the initial design session, when someone draws a box labelled "orchestrator" with arrows pointing to a cluster of boxes labelled with different capabilities — "research agent," "writing agent," "validation agent" — and calls the result an agent swarm. The diagram looks clean. It communicates capability. And it has almost no architectural content.

What the diagram does not show is what each agent owns. What it can do without asking. What it cannot do at all. What happens when it fails mid-task. How it communicates with its peers without creating invisible dependencies. How the orchestrator knows when to intervene. Where the audit trail lives. These are not implementation details to be figured out later. They are the architecture. The agent boxes are just the vocabulary. The design is in the contracts between them.

This article is about those contracts — specifically the three that matter most in practice: the autonomy boundary, the communication protocol, and the failure boundary. Getting all three right is what separates an agent system that scales from one that becomes progressively harder to reason about, debug, and govern as it grows.

The three contracts every agent must have before a line of code is written

The foundational design discipline in multi-agent architecture is the agent specification: a formal declaration, written before implementation begins, of exactly what each agent is responsible for and — equally important — what it is not. Three elements of this specification are non-negotiable.

The first is the autonomy boundary: the precise set of actions the agent may take without human review or peer-agent approval, and the set of actions that require one or the other. This boundary is not a line in the documentation. It is a policy binding that the agent's execution environment enforces. An agent that exceeds its autonomy boundary at runtime is not a misbehaving agent — it is a misdesigned one. The boundary should have prevented the action, not logged it after the fact.

The second is the communication contract: the protocol by which this agent sends and receives messages from other agents, the schema of those messages, and — critically — the guarantee about what the agent will and will not do with messages it receives. In a well-designed multi-agent system, no agent calls another agent's internal functions directly. Every inter-agent communication goes through the protocol. This is not bureaucracy. It is the isolation property that makes each agent independently deployable, independently testable, and independently replaceable without cascading side effects.

The third is the failure contract: what the agent does when it cannot complete its task. Not what it might do. What it will do, by design, in each defined failure mode. An agent that encounters an error and returns an unstructured exception to its orchestrator has no failure contract. It has a bug. An agent with a defined failure contract has specific, pre-designed responses to specific failure conditions — including a defined escalation path (to HITL, to a dead-letter queue, to a peer agent) and a defined audit record that captures the failure state for post-incident review.

Every agent node in a LangGraph state machine is an implicit failure boundary. The question is not whether you want to design the failure behaviour. The question is whether you design it deliberately or discover it in production.

What these contracts look like in practice: five agents, five specifications

To make this concrete, consider the agent architecture behind an autonomous deal desk — a system that takes an inbound sales opportunity from a CRM, retrieves pricing and contract precedents, computes margin, generates a compliant quote document, and routes the result for approval or straight-through processing. This is a real problem domain with real complexity: multiple systems of record, regulatory requirements on the outputs, a mix of deterministic computation and generative reasoning, and a hard latency target of under 90 seconds for straight-through deals.

The C4 component diagram below shows how the pipeline decomposes into five distinct agents, each with a named responsibility and an explicit place in the execution topology. What the diagram cannot show — but what the specification cards below it do — is what each agent owns, where its authority ends, and what it does when it fails.

Figure 1 — C4 component diagram: five-agent deal desk pipeline
Five agents, clearly separated responsibilities. CRM Context and RAG Retrieval are read-only by architectural declaration — they have no access to write paths. The Margin Engine is deterministic; no LLM is involved in its computation. Only the Approval Router has access to the write path, and only through a token-gated Salesforce API call. Every agent emits to Chronicle independently of the orchestrator.

The diagram shows the topology. What it cannot show is why each agent is separated the way it is — what problem each boundary solves. That requires the specification. Below is the agent spec for each of the five components, in the format that should precede any implementation: responsibility, autonomy boundary, communication contract, and failure contract.

Agent specifications — five agents, five contracts
AG-01
Orchestrator
Responsibility
Manages the ReAct loop. Receives the normalised Pub/Sub event, constructs the initial agent context, dispatches tasks to sub-agents via A2A protocol, and routes the assembled result to the Approval Router. Maximum 12 reasoning turns per execution.
Autonomy boundary
May invoke registered sub-agents only. May not write to any external system directly. May not exceed the turn limit. Any unresolved state at turn 12 is escalated to DLQ with full state dump.
Communication contract
Dispatches typed A2A messages via Pub/Sub. Receives typed result messages. No direct function calls to sub-agent internals. State persisted to Firestore at each turn boundary for recovery.
Failure contract
Turn-limit exceeded → DLQ publication with full state dump + Chronicle event. Sub-agent timeout after 30s → retry × 2 then DLQ. Chronicle emit failure → execution held (no unaudited action proceeds).
AG-02
CRM Context Agent
Responsibility
Retrieves the opportunity record, account details, pricing tier, and inventory position from Salesforce and the ERP. Normalises the retrieved data into the standard deal context schema.
Autonomy boundary
Read-only. No write access to any system. Salesforce and ERP credentials are scoped to read operations at the IAM policy level — not by convention, by binding.
Communication contract
Receives DealContextRequest from Orchestrator via A2A. Returns DealContextResult with typed fields. Schema is versioned. Breaking changes require ADR review.
Failure contract
Salesforce API timeout → exponential backoff × 3 (max 8s). If Salesforce unavailable: return typed error CRM_UNAVAILABLE. Orchestrator routes to DLQ. No partial context is used; downstream agents require complete context.
AG-03
RAG Retrieval Agent
Responsibility
Retrieves the top-3 contract precedents from AlloyDB pgvector using the deal context as the query. Returns retrieved chunks with citation references and a grounding confidence score for each.
Autonomy boundary
Read-only. No write access. Retrieval corpus has been DLP-redacted at ingestion; agent cannot retrieve raw PII. Grounding confidence below 0.6 triggers a LOW_GROUNDING flag in the result — it does not suppress retrieval.
Communication contract
Receives PrecedentRetrievalRequest. Returns PrecedentRetrievalResult with chunk array, confidence scores, and DLP-redaction status flag. Confidence score is Platt-scaled — not raw cosine similarity.
Failure contract
AlloyDB timeout → circuit breaker opens after 500ms. Returns RETRIEVAL_DEGRADED with keyword-only fallback results. Quote Generator proceeds with degraded precedent quality — flagged in the quote document and in the audit record.
AG-04
Margin Engine
Responsibility
Computes gross margin using the pricing data from the CRM Context Agent and the cost data from the ERP. Applies the configured margin floor. Returns a typed margin result with the floor-check outcome.
Autonomy boundary
Deterministic only. No LLM involvement. No retrieval. Margin computation is a pure function of its inputs. Any deal where the computed margin falls below the floor is auto-rejected — not routed for approval, rejected.
Communication contract
Receives MarginComputationRequest with typed pricing and cost fields. Returns MarginComputationResult with computed margin percentage, floor-check boolean, and a deterministic audit hash of the computation inputs.
Failure contract
BigQuery query timeout → retry × 2. If computation fails after retries: return typed error MARGIN_COMPUTATION_FAILED. Orchestrator routes to DLQ. A deal with an uncomputed margin is never routed for approval or processing — the floor cannot be verified.
AG-05
Quote Generator
Responsibility
Synthesises the quote document using Gemini 1.5 Pro with a Jinja2 template constraint. Factual fields (pricing, margin, product descriptions) are populated from typed inputs only — not generated. Gemini generates narrative text within defined template slots.
Autonomy boundary
Template-constrained generation. Gemini may not write numeric fields. All numeric values come from AG-02 and AG-04 outputs. Output is validated against a Pydantic schema before PDF render. Groundedness score below 0.6 routes to HITL with reason code LOW_GROUNDING.
Communication contract
Receives typed QuoteSynthesisRequest containing deal context, margin result, and precedent chunks. Returns QuoteSynthesisResult with PDF GCS URL, groundedness score, and Pydantic validation status.
Failure contract
Gemini API timeout → retry × 2 (30s hard limit per attempt). Pydantic validation failure → route to DLQ with schema violation detail. Groundedness below 0.6 → route to HITL, never deliver to Approval Router. RLHF label added for model improvement.

The A2A protocol: why agents must not call each other directly

The communication contract in each agent specification above references the A2A (agent-to-agent) protocol. This is not a Google-specific technology — it is an architectural discipline that predates the current wave of agent frameworks. The discipline is: agents communicate by publishing and consuming typed messages through a shared transport, not by calling each other's functions directly.

The reason this matters in practice is what happens when it is violated. An agent that calls another agent's function directly creates a coupling that is invisible at the architecture level but very visible at the operational level. If Agent B's function signature changes, Agent A breaks at runtime — not at design time. If Agent B is unavailable, Agent A either hangs or throws an unhandled exception. If Agent A needs to be replaced with a different implementation, every agent that calls its functions must be updated. None of these consequences appear in the architecture diagram. They all appear in the post-mortem.

The A2A protocol eliminates this class of problem by making the message schema the interface. Agent A publishes a typed PrecedentRetrievalRequest. It does not know or care whether Agent B, Agent C, or a batch process handles that request. The contract is the schema. The implementation is replaceable. The audit trail — because every message goes through the transport — is automatic.

Figure 2 — A2A protocol versus direct coupling: what changes when an agent fails
Direct coupling (left) makes agent boundaries invisible at runtime. The A2A protocol (right) makes the schema the interface and the transport the audit trail. Agent B can be replaced, scaled independently, or taken offline for maintenance without Agent A requiring any change — as long as the message schema contract is honoured.

Circuit breakers: the failure contract in mechanical form

The failure contract for each agent specifies what the agent does when something goes wrong. The circuit breaker is the mechanism that implements one of the most important of these: the response to a dependency that is slow or unavailable.

Without a circuit breaker, an agent that depends on a slow service will queue up requests until it runs out of resources. A 500ms timeout on the AlloyDB connection pool, compounded across concurrent executions, consumes connection slots faster than they are released. The agent degrades. Then the orchestrator degrades. Then the entire pipeline stalls in a way that is difficult to diagnose because the symptom — slow response — is far removed from the cause — AlloyDB latency.

A circuit breaker monitors the latency and error rate of a dependency and, when a threshold is exceeded, opens the circuit: subsequent requests fail fast (returning the fallback immediately) rather than waiting for the dependency to respond or time out. The circuit stays open for a configured interval, then allows a small number of probe requests through to test whether the dependency has recovered. When probes succeed, the circuit closes and normal operation resumes.

The critical design decision is what the fallback does. A circuit breaker with no fallback just converts a slow failure into a fast one — useful for system stability, but not for users. The RAG Retrieval Agent's circuit breaker, for example, does not simply fail when AlloyDB is slow: it falls back to keyword-only retrieval from a secondary index, flags the result as RETRIEVAL_DEGRADED in the message payload, and continues. The quote generator receives degraded precedent quality, flags it in the document, and the HITL threshold is automatically lowered during the degradation window — more deals route to human review, compensating for reduced retrieval quality.

Figure 3 — Circuit breaker state machine: closed, open, and half-open
The circuit breaker's three states. In CLOSED state, requests flow normally and the error rate is monitored. When the error rate or latency exceeds the threshold, the breaker opens: requests fail fast and the configured fallback is returned. After a timeout, the breaker moves to HALF-OPEN, allowing probe requests through. A successful probe closes the circuit; a failed probe returns it to OPEN. The fallback behaviour — not just the failure mode — must be designed before the breaker is implemented.

The agent smell: what to look for in a design review

The patterns described above — autonomy boundaries as policy bindings, A2A protocol as the communication interface, circuit breakers with designed fallbacks — can be checked in a design review before any code exists. The following are the specific signals that indicate a multi-agent design has not been adequately specified.

Seven signals of an underspecified multi-agent design

No autonomy boundary document. If you cannot show, for each agent, a written list of actions it may take without approval and actions that require it, the boundary has not been specified. "The agent will be conservative" is not a boundary. A policy binding is.

Agents calling each other's functions directly. Any design where Agent A invokes Agent B by calling a named function has eliminated the isolation property that makes agents independently deployable. This will look like an integration problem the first time Agent B is updated.

Failure paths described only for the happy path. A design document that shows the sequence diagram for a successful execution and does not show what happens when each step fails is describing half a system. Every LangGraph edge is a failure boundary; the diagram should show both the happy path and the failure edges.

Circuit breakers without fallbacks. A circuit breaker that only fast-fails — returning an error to the orchestrator without a defined fallback — does not solve the problem of degraded dependencies. It converts a slow failure into a fast one. The fallback is the design decision; the circuit breaker is the mechanism that invokes it.

Audit trail as an afterthought. If the audit trail is implemented as a logging call at the end of each agent's main function, it can be skipped when the function throws an exception. The audit trail should be emitted by a dedicated Audit Agent that is separate from the business logic — one that holds up the response until the emission succeeds.

State stored in the agent process. Agent state that lives only in the running process is lost when the process restarts. Firestore — or an equivalent persistent store — as the state backend is not a performance consideration. It is a recoverability requirement. An orchestrator that cannot resume from its last committed state after a restart is not a production-grade orchestrator.

The turn limit is missing or unbounded. A ReAct loop without a maximum turn limit is a loop that can run indefinitely in the presence of the wrong model output. The turn limit is not a performance knob. It is a safety boundary. Reaching it should trigger a defined fallback — DLQ publication with full state dump — not an unhandled exception.

What good design looks like from the outside

The discipline described in this article produces systems that look, from the outside, like they are almost effortlessly reliable. Agents fail gracefully. Degraded dependencies trigger compensating behaviours that users may not even notice. The audit trail is always complete. The HITL queue receives exactly the cases that require human attention, with full context, and no others.

None of this is effortless. It is the product of design decisions made before any code was written: the autonomy boundary document, the A2A schema definitions, the circuit breaker fallback specifications, the failure contracts. These artefacts are the architecture. The code is the implementation of what the artefacts specified.

The reason "agent swarm" is an architectural smell is that it names the topology — many agents connected to each other — without specifying any of the contracts. It is a noun masquerading as a design. The question to ask of any agent system, at any stage of maturity, is not "how many agents does it have?" It is: can you show me the boundary for each one, the protocol it uses to communicate, and what it does when it fails? If the answer to any of those three questions is not in writing, the design is not finished.

An agent with no defined failure contract is not a resilient agent. It is an agent whose failure mode has not yet been discovered. Production will discover it. The question is whether you designed what happens next, or whether production designs it for you.
